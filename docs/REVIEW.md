# 設計レビュー（多角的評価）

> 対象: `REQUIREMENTS.md` v3 / `DESIGN.md` / `mock/`
> 評価日: 2026-09-20
> 観点: ソフトウェアエンジニア / アーキテクト / セキュリティ / UX / PM・コンサルタント / 法務・競技倫理

## 総評

**全体設計は良質**。特に以下は高く評価できる。

- 実物の立論・参考資料からフォーマットを逆算し、データモデルに落としている（§2）。「それらしい文章生成」で終わらせない設計思想が一貫している
- 準備フェーズと本番フェーズを分離し、本番＝DB検索のみ・LLM不呼出としたのは正しい判断
- 「実資料の引用文・出典は生成しない」（§8）— ハルシネーション由来の捏造出典という最大の事故を構造的に防いでいる
- 本番パックによるオフライン冗長化をMust化している

一方、**このまま実装に入ると手戻りが発生する箇所が18件**あった。うちBlocker 4件・Major 7件は実装前に解決が必要。以下、深刻度順に示す。

深刻度の定義:
- **Blocker** — 実装後に発覚するとデータ移行・再設計が必要
- **Major** — 要件を満たせない／実装中に判断停止が起きる
- **Minor** — 品質・保守性の問題

## Blocker（実装前に必須）

### B-1. 資料番号（【資料N参照】）が立論バリエーション間で衝突する

**問題**: `DebateProject.sourceRequirements` はプロジェクト直下の配列で `number` を持つ。一方 `caseVariants` は同一論題に複数存在する（A1の中核機能）。立論パターンごとに必要な資料は異なるのに、資料番号がプロジェクト単位で一意だと:

- パターンAの【資料3】とパターンBの【資料3】が同一実体を指してしまう
- パターンを採用変更すると、立論本文中の【資料N参照】と参考資料リストの番号がずれる
- エクスポートした立論と参考資料の整合が崩れる（§12の要件を満たせない）

**影響**: 生成物の相互リンク（§14「相互リンク」ルール）が破綻。エクスポートが実用に耐えない。

**修正方針**:
- 資料の**実体**（`SourceMaterial`: 出典・引用文・種別）と、立論からの**参照**（`SourceRequirement`: どのClaimを支え、その立論内で何番か）を分離する
- `number` は「立論バリエーション内での連番」とし、採用パターン確定時に 1..N で再採番する
- 実体はプロジェクト内で共有（同じ金子宏『租税法』の引用を複数パターンで再利用できる）

### B-2. 生成ジョブの永続化が設計されていない

**問題**: §6.3で生成は「数十秒〜数分」、DESIGN §3の進捗モーダルは「閉じてもOK」と明記されている。にもかかわらず:

- データモデルに生成ジョブの実体がない（`status: "generating"` のみ。DESIGN §1・§4は「生成中 5/8」の進捗表示を要求しているが、5/8を保持する場所がない）
- Next.js のルートハンドラは実行時間に上限があり（多くのホスティングで10〜60秒、Node実行でもHTTP接続維持が前提）、数分のLLM生成をリクエスト内で完結させられない
- ブラウザを閉じたら生成が消える実装になりかねない

**影響**: 「閉じてもOK」「生成中 5/8」という明示要件が満たせない。8ステップの途中失敗時の再開もできない。

**修正方針**: `GenerationJob` エンティティ（8ステップの個別ステータス・リトライ回数・エラー・トークン消費）をDBに持ち、リクエストとは独立したワーカーで実行、クライアントはポーリングで進捗取得。ステップ単位で再実行可能にする。

### B-3. セキュリティ7要素の4つがデータモデルに存在しない

§6.2で要求しているのに、§7のデータモデルに対応する型がない:

| 要素 | 要求 | モデル上の実体 |
|------|------|----------------|
| 完全性 | 編集履歴・バージョン管理で改ざん検知 | **なし** |
| 真正性 | 誰が編集したかの識別を確保 | **なし**（User型が存在しない） |
| 責任追跡性 | 生成・編集・エクスポートの操作ログ | **なし** |
| 機密性 | プロジェクト単位のアクセス制御・他チームからの分離 | **なし**（所有者/チームの項目がない） |

**影響**: 要件の4項目が実装されない。特に編集履歴は後付けが最も高コスト（既存データに履歴がない）。

**修正方針**: `User` / `Revision` / `ActivityLog` / `DebateProject.ownerTeam` を追加し、Phase 1（雛形＋データモデル）で同時に実装する。

### B-4. 「名前を選ぶだけ」の識別では機密性と否認防止が成立しない

**問題**: §6.2は真正性を「名前を選ぶだけの簡易識別」とする一方、機密性で「プロジェクト単位のアクセス制御・他チームからの分離」、否認防止で「ログは追記型」を要求している。名前をプルダウンで選ぶだけなら他人になりすませるため、アクセス制御もログの否認防止も原理的に機能しない。要件内で矛盾している。

**影響**: 大会前の立論という秘匿情報が、URLを知る誰でも閲覧・編集できる状態になる。

**修正方針（ゼミ規模で現実的な線）**:
- **プロジェクト単位のパスコード**（チームで1つ共有）でアクセス制御を成立させる。これで「他チームからの分離」が実装可能になる
- 個人識別は名前選択のままでよい（チーム内での誰が編集したかの記録用途に限定）
- ログの否認防止は「チーム単位では成立、個人単位では参考値」と要件側で正直に格下げする（過剰実装を避ける）

## Major

### M-1. `SectionType` の定義が §7 と §8 で矛盾

§7: `type SectionType = "criteria" | "environment" | "comparison";`
§8: 「`SectionType` には `"other"` を許容し、実例にない構成も生成・登録できるようにする」

→ `"other"` を型定義に追加する。実装者が §7 をコピーすると §8 の要件が落ちる。

### M-2. 反駁・ブロックが「どの相手立論パターンに対するものか」を保持していない

`Rebuttal.targetClaimId` は Claim を直接指すが、Claim は `CaseVariant.debateCase.sections[].subsections[]` の中にある。相手の想定パターンが複数ある（`opponentCaseIds` は配列）以上、

- 同じ論点への反駁が相手パターンごとに重複生成される
- 本番モードのブロック一覧に、ほぼ同じ「返し」が何件も並ぶ（最重要画面の可用性を損なう）

**修正方針**: `Rebuttal` に `targetVariantId` を追加し、`BlockEntry` は「争点カテゴリ×相手の主張の類型」で**集約**する（複数パターンの反駁を1ブロックに束ねる）。ブロック生成ステップに重複統合を明記する。

### M-3. 本番パックの配布方式がスマホで破綻する

§6.1「本番モードはPCメインだがスマホでも完全動作」／§12「静的HTML＋Fuse.js、オフライン動作」。

**問題**: 複数ファイル構成の静的HTMLをzipで配ると、iOSではzip展開後にブラウザでローカルHTMLを開く導線が事実上ない（ファイルAppからSafariで開けず、相対パスのJS/CSSも読まれない）。Androidでも手順が煩雑で、本番直前に非情報系の学生がやる作業としては現実的でない。

**修正方針**: 二段構えにする。
1. **PWA + Service Worker**: 準備フェーズで一度サーバーにアクセスした端末は、本番モード画面とデータをキャッシュしオフライン動作（学生側の操作は「一度開いておく」だけ）
2. **フォールバック=単一HTMLファイル**: CSS/JS/データをすべてインライン化した `.html` 1枚を配布（zip不要、iOSでもダウンロード→Safariで開ける）。Fuse.jsもインライン化

複数ファイル構成のzipは採用しない。

### M-4. 「2タップ」の定義が DESIGN 内で矛盾

§10冒頭「本番中に**2タップで目的のブロックに到達**」／同表「2タップ到達 | カテゴリ→ブロック→**詳細の3階層**で完結」。画面例も3画面ある。

**修正方針**: 要件を明確に再定義する。
- **2タップで「返し」の要点が読める**（カテゴリ→ブロック一覧で、一覧カードに返しの要約を表示済み。ここで実用上完結）
- 詳細（資料・質疑・反駁）は3タップ目
- 併せて**性能目標を数値化**: 検索入力から結果表示まで200ms以内、画面遷移100ms以内（本番の1秒が勝敗に直結するため）

### M-5. スコープが過大でMVP（最低限の実戦投入ライン）が定義されていない

Must 12件・Should 5件・Could 3件＋管理6件。ゼミの実装体制でこれを一括で作ると、**大会に間に合う保証がない**。

**修正方針**: 「大会で1試合戦える最小構成」を Phase 1 として切り出す。

| 優先 | 機能 | 理由 |
|------|------|------|
| **MVP必須** | U1 論題分析 / U2 立論 / U3 資料要件 / U8 エクスポート / U14 ブロック集 / U16 本番モード / U18 本番パック | この7つだけで「準備して試合に出る」が成立する |
| 第2陣 | U5 反駁 / U4 質疑フロー / U6 比較衡量 / U15 横断検索 / A1 バリエーション生成 | 質を上げる |
| 後回し | U9 シミュレーター / U10 診断 / U12 練習問題 / U13 タイマー / U17 / U19 / U20 / A2〜A6 | なくても試合はできる |

「Must」が12件あるのは実質的に優先順位がないのと同じ。上記の3層に再編すべき。

### M-6. 永続化の方式（リレーショナル vs JSON）が未決定

「SQLite + Prisma or Drizzle」とあるが、§7のデータモデルは深くネストした文書構造。素直にリレーショナルへ正規化すると10テーブル超＋大量のJOINになり、逆に全部JSONにすると検索（U15・本番モード）が遅い。ここを決めずに始めると途中で大改修になる。

**修正方針（推奨）**: ハイブリッド。
- **リレーショナル**: `Project` / `User` / `IssueCategory` / `SourceMaterial` / `BlockEntry` / `GenerationJob` / `ActivityLog` / `Revision` — 検索・集計・リンクの対象
- **JSON列**: `CaseVariant.debateCase`（立論本文のツリー）/ `CrossExamNode.branches` — まとめて読み書きし、部分検索しないもの
- 全文検索は SQLite FTS5（日本語はbigramトークナイザ）。本番モードは事前計算した検索インデックスを配信

### M-7. API仕様・エラー設計・テスト戦略が両ドキュメントに存在しない

画面とデータモデルはあるが、その間をつなぐ契約がない。特にLLM連携は失敗が常態（レート制限・JSON構造崩れ・タイムアウト）なのに、失敗時のUX（部分生成の扱い、リトライ、ユーザーへの提示）が未定義。

**修正方針**: 実装着手時に `API.md` を起こす。最低限:
- 構造化出力は必ずスキーマ検証（Zod等）を通し、検証失敗時は自動リトライ1回→失敗ならステップ単位でエラー保持し他ステップは続行
- ユーザー向けエラーは日本語で「何が起きたか／次に何をすればよいか」を提示（非情報系ユーザー前提）
- テストは「フォーマット準拠のエクスポート」「本番モードの検索」「生成ジョブの再開」の3点を最優先で自動テスト化

## Minor

### m-1. mock に壊れたリンク

`mock/case.html` が `case_neg.html` を参照しているが、ファイルが存在しない。→ 作成する。

### m-2. 生成進捗（N/8）を保持する項目がない

DESIGN §1・§4 は「生成中 5/8」「生成状況 ✓✓✓✓✓✓○○ (6/8)」を要求。B-2 の `GenerationJob` で解決する。

### m-3. `Comparison.criteria` が争点カテゴリと紐づいていない

§14「カテゴリ軸＝争点カテゴリが全成果物の共通軸」というルールに、比較衡量表だけが従っていない（`name: string` の裸文字列）。`categoryId` を持たせる。

### m-4. Docker構成でのデータ永続化・バックアップが未指定

§6.1「Dockerコンテナで配布」「SQLite採用」「DB定期バックアップ」とあるが、ボリュームマウントの指定がない。このままだとコンテナ再作成で**全データ消失**する。`docker-compose.yml` で `./data:/app/data` を明示し、SQLiteは WAL モード（同時読み取り＋長時間書き込みジョブの両立）を前提とする。バックアップは起動時＋日次で `data/backups/` にコピーする方式を明記。

### m-5. `suggestedSources` の捏造リスク

引用文・出典は生成しない方針（§8）は正しいが、`suggestedSources`（情報源）はLLM生成のまま。存在しないデータベース名やURLが出る余地がある。→ **§2.4の実績ある情報源をホワイトリストとして内蔵し、LLMはその中から選ぶだけ**にする（自由記述を許さない）。

### m-6. `CrossExamBranch.followUpNodeId` の循環

ノード参照でツリーを表現しているため循環しうる。描画時に無限ループする。→ 保存時に循環検出のバリデーションを入れる。

### m-7. アクセシビリティ要件がない

本番モードは「大きめUI」としか書かれていない。具体値を定義する: 本番モードの本文16px以上・ボタンのタップ領域44px以上・コントラスト比4.5:1以上。低スペック端末でも読めることは可用性そのもの。

### m-8. Mermaid / React Flow が未決

質疑フロー（U4）の描画ライブラリが二択のまま。**Mermaidを推奨**: 静的SVGでよく、本番パック（オフライン単一HTML）にも埋め込みやすい。React Flow は操作性は上だがバンドルが重く、本番モードの軽量要件と衝突する。

## 法務・競技倫理（ドキュメントに記載なし＝要追加）

### L-1. 引用した文献の複製・再配布

参考資料に書籍の引用文（金子宏『租税法』等）を原文で保存し、Word/PDFにエクスポートし、さらに**事例DBで教材公開**する設計になっている。

- ゼミ内でのディベート資料としての引用は、出典明示・主従関係が保たれていれば通常問題にならない
- ただし**事例DBの「教材公開設定」で引用文込みの立論を配布する**のは範囲が変わる。公開対象・範囲を限定する運用ルールが必要
- 実物の参考資料にある「［下線はディベーターによる。］」の注記は、改変の明示として適切。この慣行をシステム側でも強制する（引用文登録フォームに注記欄を用意）

→ 要件に「引用文は出典必須・改変時は注記必須」「事例DB公開は引用文を除いた構造のみを既定とする」を追加。

### L-2. 大会規程上のAI利用可否

AI生成の立論をそのまま大会に提出してよいかは、**大会・ゼミの規程次第**。本アプリは「準備支援」と位置づけているが、成果物がそのまま提出物になりうる以上、確認せずに運用するとリスクがある。

→ §13（未決事項・リスク）に追加し、**運用前に顧問・大会要項で確認する**ことを明記。アプリ側では「AI生成／人が検証済み」のステータス表示（§6.2 信頼性）を必ず画面・エクスポートの両方で見えるようにする。

### L-3. 個人情報

メンバー氏名をエクスポート表紙に使う（実物どおり）。ゼミ内利用・ローカルサーバーなら実害は小さいが、**サーバーをインターネット公開する場合は氏名が外部到達可能になる**。→ 外部公開時はパスコード必須（B-4で担保）、事例DB公開時は氏名をマスクする。

## コスト試算（§6.3「予算未定」の補助情報）

判断材料がないと意思決定が止まるので、概算を置く。Claude API（Sonnet級、入力$3/出力$15 per 1M tokens 程度）を前提とした桁感:

| 用途 | 1回あたり | 想定回数 | 概算 |
|------|-----------|----------|------|
| 論題分析 | 入力3k / 出力2k | 5回 | 約20円 |
| 立論1パターン生成（8ステップ全体） | 入力30k / 出力15k | — | 約50円 |
| バリエーション量産（A1） | 上記×24パターン | 1回 | 約1,200円 |
| 質疑シミュレーター | 1セッション約10往復 | 20回 | 約300円 |

→ **ゼミ1論題を本気で準備して月2,000〜4,000円程度**。few-shot注入でトークンが増えるので上振れを見て月5,000円を上限目安に置けば判断できる。「予算未定で保留」ではなく、この桁ならまず走らせて A6 で実績を取る判断でよい。
