# ディベート支援アプリ（debate_app）v6

政策ディベートの準備を支援するWebアプリ。v6 では機能を2本柱に再編した。

- **自分の立論を登録して質疑で鍛える**（.docx / PDF をアップロード）
- **AIが立論・資料一式を作る**（論題から生成。1テーマにつき各側3本まで）

登録・生成どちらの立論にも、質疑と模範回答・質疑フローチャート・最終弁論の雛形・
特徴と戦い方が同じ扱いで生成される。v5（本番モード・PWA・ブロック集・反駁シート・比較衡量）
は廃止した。詳細は [v6 からの移行](#v6-からの移行) を参照。

設計ドキュメントは [`docs/`](docs/) にある。

| F11 | 質疑シミュレーター | 登録・生成の全立論から自分が守る立論／AIが演じる相手立論を選んで練習 |
| F12 | エクスポート | 立論・資料（Word、統計の表・グラフ入り）、質疑フローチャート、最終弁論雛形（印刷・PDF） |

## セットアップ

```bash
npm install
cp .env.example .env
npm run db:migrate
npm run dev
```

`.env` の主な変数（詳細は `.env.example` のコメントを参照）。

| 変数 | 内容 |
|------|------|
| `ANTHROPIC_API_KEY` | Claude APIキー。**これがないと生成機能が一切動かない** |
| `DEBATE_APP_PASSWORD` | ゼミで共有する合言葉。これを知っている人だけがログインできる |
| `DEBATE_MODEL` | 立論・質疑・最終弁論など、推論が要る生成に使うモデル（既定 `claude-sonnet-5`） |
| `DEBATE_MODEL_LIGHT` | 見出し判定・引用箇所や統計表の選択・Web検索など軽い処理に使うモデル（既定 Haiku）。結果はコードで検査してから保存するので安いモデルでよい |
| `DEBATE_DATA_DIR` | データの保存先。Dockerではボリュームをここにマウントする |
| `ESTAT_APP_ID` | e-Stat APIのアプリケーションID。未設定だと統計資料は「作成手順」の表示になる |
| `DEBATE_SESSION_SECRET` | 任意。未設定なら合言葉から導出する |
| `DEBATE_CHART_FONT` | 任意。統計グラフ（Word）用の日本語フォントファイル。Dockerでは不要 |
| `DEBATE_MAX_CONCURRENT_JOBS` | 任意。同時に進める生成ジョブ数。既定 2。Fly.ioのマシンはメモリ512MBのため、上げすぎるとメモリ不足で落ちる |

APIキーはサーバー側だけで使う。`NEXT_PUBLIC_` を付けるとブラウザに露出するので付けないこと。
合言葉が未設定だと誰もログインできない（誤って公開状態になるのを防ぐため、そういう挙動にしてある）。

### 使い方

1. 各自が自分のPC・スマホからサーバーのURLを開く
2. 合言葉と名前を入れてログイン（名前は「誰が直したか」の記録用）
3. テーマ（論題）を登録
4. 立論を**アップロード**（自作）するか、**生成**（AI）する
5. 質疑・フローチャート・最終弁論雛形・特徴と戦い方は自動で生成される
6. 練習（タイマー・ペースメーカー・質疑シミュレーター）とエクスポートで仕上げる

### Docker で動かす

```bash
docker compose up -d
```

`./data` をボリュームマウントしている。**これを外すとコンテナを作り直した瞬間にデータが消える。**

### ゼミで使う（Fly.io）

手順は [docs/DEPLOY.md](docs/DEPLOY.md)。配るのは**URL 1つだけ**。

**Vercelには乗らない。** ファイルシステムが永続せずSQLiteが消え、
レスポンス後に関数が終了するため数分かかる生成が完走しない。

## 設計上、特に注意すべき点

実装を引き継ぐ人が最初に踏みやすい落とし穴。

### 1. 資料番号は「立論ごと」にスコープされる

`【資料N参照】` の N はプロジェクト全体で一意ではない。立論（`CaseVariant`）ごとに 1..N で、
資料の実体（`SourceMaterial`）はプロジェクト内で共有される。

立論を編集したら必ず `validateVariant()` を通すこと。資料番号を登場順に振り直し、
本文中の `【資料N参照】` も同時に書き換える。ここを飛ばすと、立論と参考資料の番号がずれて
エクスポートが使い物にならなくなる。

### 2. 生成はHTTPリクエスト内で完結させない

生成は数分かかり、「ブラウザを閉じてもOK」が要件。`GenerationJob` をDBに作り、
バックグラウンドで進める。v6 では**立論1本につき1ジョブ**（登録は import ジョブ、
生成は analysis→case_outline→case_body→source_plan→source_fetch→number_check→
cross_exam→closing→strategy の各ステップ）。クライアントは `/api/jobs/:id` を
ポーリングする。ステップ単位で状態を保存しているので、途中で失敗しても
**失敗したステップだけ再実行**できる。

同時に進めるジョブ数は `DEBATE_MAX_CONCURRENT_JOBS`（既定2）で制限している
（`src/lib/jobs/runner.ts`）。Fly.ioのマシンはメモリ512MBで、PDF処理・AIへの
並列問い合わせ・グラフ画像作成が重なるとメモリが足りなくなるため。

サーバーが再起動すると、途中で止まっていたジョブは次の起動時に自動で再開する
（`src/instrumentation.ts` → `resumeOnBoot()`）。Fly.ioは使われていない間マシンを
止めるため、これがないと長い生成が復帰しない。

### 3. AIに書かせないもの（捏造防止）

v5 は「引用文・出典は一切書かせない」だったが、v6 では**実在を機械的に確かめられたものだけ**
AIに埋めさせる。

- **引用文** — 取得したページ本文に**実際に存在する文字列**のみ採用する。保存前にコード側で
  本文との一致を検査し（`domain/quote.ts`。空白・改行・全半角を正規化した上で部分一致）、
  一致しなければ不採用にする
- **法令の条文全文** — e-Gov から取得する（LLMに書かせない）
- **統計値の計算** — 割合・伸び率・一人当たり等は`domain/statistics.ts`のコードが計算する。
  LLMは式の選択だけを行う
- **情報源** — `source-whitelist.ts` で許可したドメイン（`go.jp` 配下、`nii.ac.jp`）からのみ
  取得する。範囲外は取得しない（リダイレクト先も検査）
- **数字の根拠** — 立論・資料に出てくる数字は、出典（統計名・年次・URL・最終確認日）に
  結びついているかをコードで検査する（`domain/numbers.ts` → `number_check` ステップ）。
  生成立論では出典のない数字を本文から除く

### 4. 立論は5分。分量が品質

読み上げ5分を超えても、30秒以上余らせても減点される。適正は**4分30秒超〜5分00秒**の
30秒幅しかない。速度で帳尻を合わせるのは不可で、**文字数そのもの**を適正にするしかない。
基準は実物（`docs/samples/`）から取った320字/分・約1,600字。`domain/speech.ts` がこの計算を持つ。

生成側は `case_body` ステップで字数をコードで数え（`countSpeechChars`）、範囲に収まらなければ
削る／補うの自動調整を最大2回行う。それでも外れたら警告付き（`lengthWarning`）で保存する。

### 5. 読み上げ支援に音声認識を使わない

「声を拾ってリアルタイムにペース指示を出す」案は見送った。日本語の専門語は誤認識が集中し、
誤指示が早口を招くため。代わりに `domain/pacing.ts` のペースメーカーを置いた。
経過時間から「ここまで来ているべき」段落を出すだけで、誤作動が原理的に起きない。

### 6. 品質向上はfew-shotで行う（FTしない）

`domain/exemplars.ts` に実際の試合で使われた立論を埋め込み、生成時に「同じ側のお手本」を
提示している。真似させるのは**構成・一文の密度・分量**の3つだけだとプロンプトで明示している。
ファインチューニングは選ばない（Claude APIが非対応であることに加え、学習データが実物2件しかない）。

### 7. AI生成物であることを隠さない

生成・取得直後は未検証の状態（`origin` が `ai_fetched` / `generated` 等）。
画面にもエクスポートにも「AI生成（未確認）／確認済」を必ず表示する。LLMの法解釈・資料の
選び方は誤りうるので、人のレビューを挟む前提で作る。

### 8. PDFはサーバーで作らない

PDFは印刷ビュー（`/projects/[projectId]/print/[kind]`）＋印刷CSSで、ブラウザの
「PDFに保存」を使う。Puppeteerを入れるとDockerイメージにChromiumが乗って約400MB増える
うえ、日本語フォントを入れ忘れると文字が豆腐になる。印刷CSSならフォントはOS任せで、
どのPCでも同じ結果になる。

Wordは `docx` ライブラリで実体のある .docx を返す（書式の再現が要件のため）。
統計グラフはSVGをコードで組み、`@resvg/resvg-js` でPNG化してWordに貼る
（Dockerでは `fonts-noto-cjk` が必要）。

## v6 からの移行

- v5 のデータは**引き継がない**。デプロイ・マイグレーション時に v5 のDBを検知すると、
  自動的に `data/backups/debate-v5-<日時>.db` へ退避し、v6 は空のDBから始める
  （`src/db/migrate.ts`）。手元のデータが必要な場合はこのバックアップから読み出す
- v5 の本番モード・PWA/Service Worker・ブロック集・反駁シート・比較衡量・練習問題モード・
  横断検索・管理機能は削除した
- URLの `projects` → `themes` のような改名は行っていない（内部・URLとも `projects` のまま）

## 現在の状況

### 実装済み

F1〜F12（上記機能一覧）と、テーマ・立論一覧・立論詳細（本文／資料／質疑／フローチャート／
最終弁論／特徴と戦い方の各タブ）・練習・エクスポートの各画面。ログイン、生成ジョブ基盤
（永続化・自動リトライ・部分失敗の許容・再開）、資料番号の不変条件、字数の自動調整、
資料取得エンジン（法令・国会・統計・論文・官公庁／判例のWeb検索経由取得）、引用文の照合、
数字の検査、質疑フローチャート、最終弁論雛形、特徴と戦い方、Docker配布構成、
Fly.ioデプロイ設定。

### この開発環境では検証できないこと

実際の官公庁サイト・e-Gov・国会会議録・e-Stat・CiNiiへの資料取得は、この開発環境（アプリ内
ブラウザ等）からは外部の実サイトに到達できない場合がある。政府サイトへ到達できる環境
（自分のPCかFlyのマシン上）で

```bash
npm run spike:sources
```

を実行し、資料5本の取得成功率と失敗理由を確認すること。

### 既知の制約

- **Fly.ioのauto-stopで生成が一時停止する** — マシンは使われていない間停止する
  （コスト削減のための意図的な設定。`fly.toml` の `auto_stop_machines = "stop"`）。
  停止中に走っていた生成ジョブはそこで止まり、**次にアクセスがあってマシンが起動した
  ときに続きから自動で再開する**（`src/instrumentation.ts`）。生成中に長時間アクセスが
  ないと、完了通知が遅れる
- **質問数はプロンプト頼みではないが、完全な保証ではない** — 段落×攻撃点の
  網羅はコードで表を先に作ってLLMに埋めさせ（試合で使う質疑はゼミ生が選ぶ）、
  実際の質問文の質・厳密な網羅はプロンプトに依存する部分が残る
