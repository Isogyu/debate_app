# ディベート支援アプリ（debate_app）

政策ディベートの**準備〜本番**を支援するWebアプリ。
論題を入力すると、肯定側・否定側の立論・資料要件・質疑・反駁・ブロック集を
一貫した論証構造として生成し、本番では争点カテゴリから2タップで「返し」を引ける。

設計ドキュメントは [`docs/`](docs/) にある。

| ドキュメント | 内容 |
|--------------|------|
| [docs/REQUIREMENTS.md](docs/REQUIREMENTS.md) | 要件定義・データモデル・生成パイプライン（v4） |
| [docs/DESIGN.md](docs/DESIGN.md) | 画面設計・ワイヤーフレーム |
| [docs/REVIEW.md](docs/REVIEW.md) | v3に対する多角的レビューと修正方針 |
| [docs/mock/](docs/mock/) | 全画面の静的HTMLモック（`index.html`が起点） |
| [docs/samples/](docs/samples/) | 実物の立論・参考資料（フォーマットの基準） |

## セットアップ

```bash
npm install
cp .env.example .env        # ANTHROPIC_API_KEY を設定する
npm run db:migrate
npm run dev
```

APIキーはサーバー側だけで使う。`NEXT_PUBLIC_` を付けるとブラウザに露出するので付けないこと。

### Docker で動かす

```bash
docker compose up -d
```

`./data` をボリュームマウントしている。**これを外すとコンテナを作り直した瞬間にデータが消える。**

## 構成

```
src/
  domain/          ドメイン層（フレームワーク非依存）
    types.ts           データモデル（REQUIREMENTS §7）
    invariants.ts      不変条件。資料番号の再採番・循環検出・引用ルール
    schemas.ts         LLM構造化出力のZodスキーマ
    source-whitelist.ts 情報源ホワイトリスト（捏造防止）
    case-format.ts     立論の整形と【資料N参照】の解析（純粋関数）
  db/              永続化（Drizzle + SQLite/WAL）
  lib/
    llm/             LLM抽象化レイヤ（差し替え可能）＋プロンプト
    jobs/            生成ジョブのランナーと8ステップ
  app/             画面・APIルート
  components/
tests/             不変条件のテスト
docs/              設計ドキュメント一式
```

## 設計上、特に注意すべき点

実装を引き継ぐ人が最初に踏みやすい落とし穴。詳細は
[docs/REVIEW.md](docs/REVIEW.md) を参照。

### 1. 資料番号は「立論パターンごと」にスコープされる

`【資料N参照】` の N はプロジェクト全体で一意ではない。
同一論題に複数の立論パターンがあり、それぞれ必要な資料が違うため、
**番号は `CaseVariant` の中で 1..N**、資料の実体（`SourceMaterial`）は
プロジェクト内で共有される。

立論を編集したら必ず `validateVariant()` を通すこと。
資料番号を登場順に振り直し、本文中の `【資料N参照】` も同時に書き換える。
ここを飛ばすと、立論と参考資料の番号がずれてエクスポートが使い物にならなくなる。

### 2. 生成はHTTPリクエスト内で完結させない

生成は数分かかり、「ブラウザを閉じてもOK」が要件。
`GenerationJob` をDBに作り、バックグラウンドで8ステップを進め、
クライアントは `/api/jobs/:id` をポーリングする。
ステップ単位で状態を保存しているので、途中で失敗しても
**失敗したステップだけ再実行**できる。

### 3. AIに書かせないもの

- **引用文・出典** — 存在しない出典の捏造になる。資料要件（何を証明すべきか・どう探すか）だけ生成する
- **法令の条文全文** — e-Gov等から取得し、`LawRef.verified` を立てる
- **情報源** — `source-whitelist.ts` のIDから選ばせる。範囲外は `sanitizeSuggestedSourceIds()` が落とす

### 4. 本番モードは別物として扱う

読み取り専用・グローバルナビなし・LLM不呼出。
検索対象は事前計算済みの `BlockEntry.searchText`、データは一度に
クライアントへ渡しきり、試合中にサーバーへ往復しない。
目標は画面遷移100ms・検索200ms。

### 5. 生成は分析でいったん止まる

8ステップのうち `analysis` だけを先に走らせ、**人が分析確認画面で承認するまで
残り7ステップを流さない**（`runJob(jobId, { only: ["analysis"] })`）。
LLMの法解釈は誤りうるので、間違った分析のまま立論まで作ってしまわないための関門。
承認時は `runJob(jobId)` を呼ぶだけでよい（済んだステップは自動で飛ばされる）。

### 6. AI生成物であることを隠さない

生成直後は `Revision.origin = "ai"` の未検証状態。
画面にもエクスポートにも「AI生成（未確認）／確認済」を必ず表示する。
LLMの法解釈は誤りうるので、人のレビューを挟む前提で作る。

## 未確認のリスク

運用開始前に確認すること（[docs/REQUIREMENTS.md](docs/REQUIREMENTS.md) §13）。

- **大会規程上のAI利用可否** — 成果物がそのまま提出物になりうる。顧問・大会要項で要確認
- **大会日程** — MVP（Phase 1〜5）の期限を大会日から逆算して決める必要がある
- **引用文献の再配布範囲** — 事例DBでの教材公開は、ゼミ内の引用とは範囲が異なる
